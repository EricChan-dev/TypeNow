### [x] 1. 首页头像体积 ✅ 已修

现状：`src/app/(public)/page.tsx` 的信任行用 4 个普通 `<img>` 显示头像，
但源文件是 **1000×1000 / 每张 80–112KB / 合计约 384KB**，实际显示尺寸只有 **20×20 CSS px**。

为什么值得修：像素量是需要的约 2500 倍。移动网络上这 384KB 会明显推迟首屏。

顺带：这 4 张图被 React 19 自动加了 `<link rel="preload" as="image">`，
Chrome 因此报 "preloaded but not used"（16 条同类警告的一部分）。
改成 `next/image` 且**不加 `priority`** 之后 preload 不再发送，警告一并消失。

做法：已换成 `next/image`，`width/height = 40`，**不加 `priority`**。

实测结果（`next start` + 抓真实响应）：

### ⚠️ 一条必须记住的功能边界：全库搜索**只支持纯中文**

这不是偷懒，是实测出来的硬限制 —— 已把数字写进
`src/lib/sentence-search.ts` 的模块注释与单测，避免以后有人"顺手放开"：

| 关键词 | MATCH（全文索引） | LIKE（旧口径） | 结果 |
|---|---|---|---|
| 天气 / 学习英语 / 动物保护 / 来吧 / 第一位的 | 与 LIKE **完全一致**（7/7） | — | ✅ 可靠 |
| `James` | 4414 | 94 | ❌ 多 47 倍 |
| `jame` | 68640 | 94 | ❌ 多 730 倍 |
| `det.` | 44621 | 217 | ❌ 多 205 倍 |
| `与Allen` | 1331 | **0** | ❌ 凭空造出 1331 条 |
| `jam` | **0** | 4 | ❌ 明明包含却搜不到 |

受控实验（4 行内容已知的表）复现：`"james"` 带引号短语返回第 1、2、3 行，
而第 2、3 行**根本不含** james（只有 `am`/`me`/`es` 这些 bigram）。
**引号短语对 ASCII 不强制相邻，对中文强制。**

所以现在的规则是：**全库搜索只接受纯中文（≥2 字）；纯英文与中英混合返回 400，
要求先选课时**（课时内是 LIKE 精确匹配，中英文都准确）。

**如果以后要做英文全库搜索**，可行的方向是再加一个**默认解析器**的 FULLTEXT 索引，
查询时用 `FORCE INDEX` 指定解析器（已在临时库验证：`FORCE INDEX (ft_words)` 下
`james`→1、`games`→2，结果正确）。代价：drizzle 的查询构造器无法注入 `FORCE INDEX`
（它在 FROM 子句），得为这条路径写裸 SQL，或者再加一个同内容的生成列
（但那要再重建一次表，约 16 分钟）。**没有做，是因为收益不抵复杂度。**

## 四、上线流程备忘（容易忘的四条）

1. **⚠️ 对 `deploy.sh` 本身的改动，要「下一次部署」才生效。**
   因为 webhook 执行的是服务器上**当时那份** `deploy.sh`：它先 `git pull` 拉到新脚本，
   但已经跑在内存里的流程用的还是旧逻辑。
   2026-09-29 加主动触达的 crontab 安装时实际踩到 —— 第一次部署的日志里根本没有
   那一步，要再跑一次 `deploy.sh` 才装上。
   **判断方法**：部署完检查日志里有没有你新加的那一步；没有就再跑一次。
2. **⚠️ 绝不要用 scp 往服务端仓库目录里放文件。**
   `deploy.sh` 依赖**干净的工作区**：往里扔一个未跟踪文件，只要这个名字之后被提交，
   下一次 `git pull` 就会以「untracked working tree files would be overwritten by merge」
   失败。2026-09-30 实际踩到 —— 我为了跑诊断脚本把 `scripts/test-notification.ts`
   scp 到服务器，之后该文件被提交，导致下一次 webhook 部署连续 5 次拉取失败。
   （deploy.sh 会正确中止、不构建不重启，线上维持原版本，所以没有发错版本；
   但那次发布被静默漏掉了，要人工补跑。）
   要在服务器上跑临时脚本：传到 `/tmp`，用 `npx tsx /tmp/x.ts` 跑；
   需要放进仓库目录的用 `git` 走（提交 → 部署）。
3. **迁移是手工执行的**：仓库没有迁移执行器。新增 `db/migrations/*.sql` 后必须
   手工在生产库执行（见 `db/README.md`）。执行前先按 `db-backup/` 的惯例备份。
4. **注意 DDL 与代码的先后顺序**：
   - 代码依赖新列/新表（如 `00016`/`00020`）→ **先执行 DDL，再部署代码**
   - 数据修正是"清掉旧解析结果"这类（如 `00019` 清单词缓存）→ **先部署代码，再执行 DDL**
     否则旧代码会把缓存重新灌成坏数据
