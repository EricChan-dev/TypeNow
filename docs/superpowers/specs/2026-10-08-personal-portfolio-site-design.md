# 个人作品集站（dev.typenow.cn）— 设计文档

> 2026-10-08。把陈应帅的个人简历做成面向求职的在线作品集站，挂在新子域 `dev.typenow.cn`，
> 与现有 `typenow.cn`（TypeNow 码上英语）完全隔离：独立仓库、独立进程、独立端口。

## 1. 背景与目标

### 1.1 现状

- 简历是静态 PDF（`陈应帅-全栈工程师.pdf`），只能整体浏览，无法按需跳读。
- 已有一台阿里云服务器（2 vCPU / 3.5GiB 内存 / 40G 磁盘），跑着 TypeNow 与 webhook 两个 pm2 进程：
  - `typenow` → `:3000`（Next.js 16，`/home/admin/TypeNow`）
  - `webhook` → `:9000`（GitHub 自动部署）
- nginx 只有 `/etc/nginx/conf.d/typenow.conf` 一个站点配置，`server_name typenow.cn www.typenow.cn`，
  全量反代到 `127.0.0.1:3000`。
- Let's Encrypt 证书位于 `/etc/letsencrypt/live/typenow.cn/`，**SAN 仅含 `typenow.cn, www.typenow.cn`**。

### 1.2 目标

做一个**求职导向**的个人站，而不是「个人主页」。评判标准不是「看过觉得不错」，
而是**让面试官在 90 秒内决定约面试**。

读者分两层，站点结构必须同时对两层友好：

| 读者 | 停留时间 | 需要拿到什么 |
|---|---|---|
| HR / 招聘方 | ~30 秒 | 是谁、几年、什么级别、怎么联系 |
| 技术面试官 | 3–5 分钟 | 技术深度、架构判断力、取舍能力 |

### 1.3 非目标（本次不做）

- **`english.typenow.cn`**：讨论过把 TypeNow 主站迁到子域，本次不做。
  `typenow.cn` 保持现状，零改动。
- **`test.typenow.cn`**：用户已明确砍掉（m00097）。otest 的介绍并入本站，不另开门户。
- **博客 / 技术文章系统**：没有持续写作的内容源，做出来就是空栏目。
- **双语版本**：先做中文单语。
- **评论、访问统计、暗色模式**：与「90 秒内决定约面试」无关。

## 2. 已拍板的决策（含被否决方案与理由）

### 2.1 架构：新建独立仓库 + 单域 Next 应用

**决策**：新建仓库 `EricChan-dev/dev-typenow`，一个 Next.js 应用，监听 `:3001`（仅绑 `127.0.0.1`），
对外通过 nginx 的 `dev.typenow.cn` 反代。

**被否决的方案**：

- **A 三个独立项目各一个 pm2 进程**：用户最初提过 `dev / test / english` 三个域名。
  否决理由：2 核 3.5G 的机器上已经 **Swap 用掉 1410MB**，再常驻两份 Node 进程会加剧内存压力；
  且三套依赖、三套部署流程，维护成本与收益不成比例。test 域名砍掉后更无必要。
- **B 一个 Next 应用用 middleware 读 Host 头分流三个域名**：曾是我的推荐方案。
  在 test 域名砍掉、english 域名本次不做之后，**middleware 分流不再需要**，
  退化为普通单域应用。
- **C 作品集站静态化**：内容几乎不变，静态化确实省内存。
  否决理由：项目详情页与「点击才显示联系方式」都需要少量客户端逻辑；
  而且静态站要另配一套构建与部署流程，与现有 pm2 部署体系不一致，长期维护反而更麻烦。

**为什么独立仓库而不是塞进 TypeNow 仓库**：两个站的技术栈与内容完全无关
（TypeNow 是 MySQL + Drizzle 的应用，作品集站是纯内容站），
合在一起会让 TypeNow 每次部署都重构建无关代码，也会让 webhook 触发逻辑变复杂。

### 2.2 视觉风格：杂志编辑感（B）

在八个候选方向中选定。**关键约束：「编辑感」只加在标题与留白上，不加在正文上。**

- 标题层：衬线大字（`Georgia` / `Songti SC`）+ 斜体强调色 `#b45309` + 米白底 `#faf8f5`
- 正文层：无衬线（`ui-sans-serif`）+ 等宽数字标注年份

这样 HR 感受到的是「像一本杂志的深度报道」，技术面试官看到的仍是干净的技术信息，
避免滑向「个人博客」的观感。

**被否决的方向**（完整预览见 `timeline-all-directions.html`）：
A 深色技术感（略常规）、C 章节编号式（太安静）、D 横向轨道式（移动端要维护两套布局）、
E 成长曲线式（纵轴指标要能自证）、F Git 提交史式（HR 看不懂）、
G Bento 卡片墙（丢失成长叙事）、H 能力解锁对照式（视觉太弱）。

> 注：**H 的信息结构没有被丢弃**。「做过的事 → 因此能负责」的翻译逻辑，
> 融进了第 2.3 节的心路历程文案里；B 只是承载它的视觉皮肤。

### 2.3 心路历程：五级台阶时间线

形态为「时间线 + 节点标题 + 短描述」，**不写散文**。主轴：

```
写页面 → 建体系 → 跨端 → 架构 → 平台 + AI
```

| 2021 | 阳光保险 | 跨端与原生底座 | 自研 JSBridge + RN 容器，抹平 iOS/Android WebView 差异，可维护性 +50% |

**主动交代时间线缺口**：简历写「11 年工作经验」，但最早的工作经历条目是 2018.07，

### 2.4 联系方式：点击才显示

简历上的手机号 `166****2010` 与邮箱 `166****2010@163.com` 含同一个号码。
明文上公网后会被爬虫抓走，导致常年推销电话。

**决策**：页面只显示「查看联系方式」按钮，点击后由 JS 从打散的片段拼出号码。
HR 零操作成本，爬虫拿到的是空文本。

否决了「图片化展示」（无法复制、移动端不便、现代 OCR 仍可能识别）与
「换成不含手机号的邮箱」（用户希望保留现有联系方式）。

### 2.5 项目详情页深度：决策导向

每个项目详情页固定五段，**不贴代码**：

1. **背景与目标** — 解决什么问题，成功标准是什么
2. **我的角色** — 是独立负责还是参与某部分
3. **架构** — 文字 + 简单框图
4. **关键取舍** — 为什么这么选，放弃了什么（**这是全页价值最高的部分**）
5. **结果** — 量化产出

**被否决的方案**：工程师级深潜（加接口设计、表结构、时序图、代码片段）——
工作量翻倍，且部分内容涉及前公司保密事项；
先做轻量版（5–8 句 + 截图）——不足以支撑「技术面试官看深度」这层读者。

三个「其他经历」（易借钱贷款超市、阳光互联网医院、惠金所 APP）**不做详情页**，
在作品区以一行小条目呈现。

### 2.6 技术栈呈现：分组 + 使用年限

五组，每组一行标签：`FRONTEND / BACKEND / DATA / AI / INFRA`。

- 每项后面跟**实际使用年限**（例如 `Vue 3  7y ⋆`），用 `⋆` 标主力技术
- 不用星级评分（主观且不可验证）
- 每项都必须有真实项目背书（不刷关键词）
- AI 组视觉高亮，因为这是差异点

**年限数据必须由用户逐项核准后写入**——写错的年限比不写更糟，
面试官一句「这个你用了几年」就能验证。

### 3.3 项目详情页内容（otest 为例）

**背景与目标**：测试团队要覆盖几十款真机，过去靠人工借机器、手工回归，
设备利用率低且结果不可追溯。目标是让测试同学在浏览器里直接操作真机并自动生成用例。

**我的角色**：独立负责全栈——领域建模、四端架构设计、WebSocket 实时链路、AI 能力接入与部署编排。

**架构**：

```
Vue 3 管理端（云端）
  │ HTTP / WebSocket
Spring Boot 服务端   · JWT/RBAC · Quartz · MySQL · Redis
  │ WebSocket 实时链路（注册鉴权 / 设备发现 / 心跳保活 / 状态同步 / 异常重连）
Java 设备 Agent      · ADB · scrcpy/minicap · WDA · MJPEG / H.264
  │ 本地会话
真机集群              另有 Electron 桌面端用于本地调试
```

**关键取舍**（四条）：

1. **用 WebSocket 长连接而不是轮询** — 设备状态变化频繁，轮询在几十台设备下会把服务端打满；
   代价是要自己实现心跳、重连与状态补偿。
2. **画面传输分离：MJPEG 与 H.264 双路径** — 低端机用 MJPEG 保证兼容，主流机用 H.264 换流畅度；
   代价是 Agent 侧要维护两套编码。
3. **大模型放在「生成/修复用例」而不是「执行控制」** — 执行链路要确定性，不能有幻觉；
   AI 只进确定性要求低、价值高的环节，并保留人工确认。
4. **服务端与设备 Agent 分离部署** — Agent 要贴近设备、直连 ADB，
   放同一进程会让扩容与故障隔离都变难。

**结果**：设备连接成功率 98%+；用例编写从手工逐条录入改为 AI 生成 + 人工确认；
Docker Compose 一键起全栈，nginx 统一代理 HTTP 与 WebSocket。

### 3.4 TypeNow 详情页要点

- 从产品设计、数据建模到部署运维全部独立完成
- Next.js 16 + React 19 + Tailwind v4 + MySQL（Drizzle ORM）
- 自建服务器：pm2 + nginx + Let's Encrypt，GitHub webhook 自动部署
- 含发音评分（有道 API，逐词评分与多维评分）、练习计分、定时生命周期任务

## 4. 服务器侧改动清单

现有 `typenow.conf` **有一个已存在的 bug**：`location /webhook` 嵌套在 `location /` 内部，
括号层级错乱。**本次不动它**，新站另开一个配置文件。

| # | 改动 | 说明 |
|---|---|---|
| 1 | 新建 `/etc/nginx/conf.d/dev-typenow.conf` | 独立 server 块，`server_name dev.typenow.cn`，反代 `127.0.0.1:3001` |
| 2 | certbot 重签证书 | 现有 SAN 只有 `typenow.cn, www.typenow.cn`，必须加 `dev.typenow.cn`；可沿用同一张证书挂多个 server 块 |
| 3 | pm2 新增进程 | 以 **admin** 用户启动（pm2 空间属 admin，`/home/admin/.pm2`），端口 `:3001` 仅绑 `127.0.0.1` |
| 4 | 代码目录 | `/home/admin/dev-typenow`，与 `/home/admin/TypeNow` 平级 |
| 5 | 部署脚本 | 参照 `TypeNow/deploy.sh` 的成熟做法：`flock` 串行化、`git pull --ff-only` 带重试、构建到 staging 目录再原子切换、保留上一版 |
| 6 | 防火墙 | 不新开端口，对外只保留 80/443 |

**资源约束（实测）**：内存 3635MB total / 1312 used / 2080 available，
**Swap 2047MB 已用 1410MB**（内存压力已存在）；磁盘 40G 用 16G，余 25G。

新站是纯内容站，构建产物小、运行内存低，但仍应确认新进程常驻内存后
不把已有 Swap 压力推到危险区。**这是上线前必须实测的一项。**

## 5. 验证

### 5.1 内容层面

- 点击「查看联系方式」后号码正确显示
- 时间线五个节点齐全，2015–2018 缺口说明存在

### 5.2 部署层面

- `curl -I https://dev.typenow.cn` 返回 200 且证书 SAN 含 `dev.typenow.cn`
- `curl -I https://typenow.cn` **仍然 200**（确认没有把老站弄坏）
- `pm2 list` 中 `typenow` 与 `webhook` 仍 online
- `free -m` 的 Swap 使用量没有显著恶化
- 在 1440px 与 390px 两个宽度下各看一遍首屏

### 5.3 上线前必须真机验证的一件事

**新进程常驻后的内存表现。** 本机已存在 Swap 压力，
需要在新进程启动并跑一段时间后实测 `free -m`，确认不会触发 OOM 拖垮 TypeNow。

## 6. 回滚

- `pm2 delete` 新进程 + `rm /etc/nginx/conf.d/dev-typenow.conf` + `nginx -s reload`
- 证书重签是**追加 SAN**，不影响原有域名；如需回滚，certbot 重新签一张只含
  `typenow.cn, www.typenow.cn` 的即可
- 全过程不触碰 `typenow.cn` 的任何配置，**老站零风险**
