# 跟读评分改版 — 设计文档

> 2026-09-30。把跟读评分从「练习页里一行小字」改成**独立弹窗 + 逐词评分 + 多维进度条 + 总评与评语**，
> 并把评分落库，使其在历史回看时可见。

## 1. 背景与问题

### 1.1 现状（读码所得，不是推测）

`src/components/home/learn/VoicePanel.tsx`（499 行）挂在练习页句子下方，是**内联**的一小块：

- 两个按钮：`朗读`（TTS）、`跟读评分`
- 停止录音后转 WAV → `POST /api/youdao/evaluate` → 结果**内联**渲染：
  - 一个圆形总分
  - 准确度 / 流利度 / 完整度 三个**小字数字** + 语速
  - 逐词分数做成**一行彩色小标签**（chip）

**后端其实已经不薄**：`lib/pronunciation.ts` 的 `mapYoudaoEvaluate` 已经返回
`score / accuracy / fluency / integrity / speed / words[]`，且**刻意保留词分的 `null`**
（`?? 0` 会把"字段缺失"显示成"0 分"，用户以为全读错了）。

所以这次改的是**呈现与留存**，不是评分能力本身。

### 1.2 四个具体问题

1. **没有独立空间**：评分结果挤在句子下面，逐词分只是一行小标签，看不出"哪个词拖低了总分"
2. **没有评语**：只有数字，用户不知道下一步该练什么
3. **不留存**：`result` 是组件内 state（`useState`），且与句子绑定；换句、刷新即丢失
4. **维度只有数字**：没有可视化，三个数之间谁高谁低要读数字才知道

### 1.3 一个必须一并处理的数据事实

库里 `sentences.english` 的**标点是独立 token**，实测样本：

```
Seven , eight , don't be late ! Nine , ten , take your pen
You can change the volume by pressing this button
```

第一句的 `,` `!` 两侧都有空格 → 它是被当作独立"词"存的。
**逐词评分不能按这个字段切词** —— 有道的分词与它不一定一致。逐词一律用
有道返回的 `words[]`，理由见 §3.3。

## 2. 目标与非目标

### 目标

- 跟读评分有**独立弹窗**，句子为骨架、每个词的分数挂在词下面
- 整句从**多个维度**评分，以**进度条**呈现
- 汇总为**总体评分 + 一句评语**
- 关闭弹窗后评分**留在练习页**，点击可**重开详情**
- 可**再试一次**
- 评分**落库**，历史回看时可见

### 非目标（本次不做）

- **进步曲线**（"这句从 61 涨到 84"的跨会话趋势）—— 只留**最新一次**，
  没有多行尝试记录，所以曲线没有数据源。这是刻意的取舍，见 §3.2
- **音标级诊断**（"volume 的 /v/ 发成了 /w/"）—— 需要音素级数据或 AI，
  规则做不到，不该假装能做到
- 移动端录音（现状是桌面 Chrome/Edge；本次不动）
- 跟读评分与练习进度、奖励、复习队列的任何联动

## 3. 已拍板的决策（含被否决方案与理由）

### 3.1 弹窗布局：句子为骨架，分数挂在词下面

三个候选（见可视化伴侣的三张草图）：

| 布局 | 信息顺序 | 结论 |
| --- | --- | --- |
| A 结论先行 | 总分评语 → 维度 → 词 | 主流做法，但"哪个词拖低了分"要往下找 |
| B 词 → 维度 → 总分 | 诊断感最强 | 结果要滚到最后才看到 |
| **C 句子为主** | 词（带分）→ 维度 → 总分评语 | **采用** |

选 C 的理由：这是**朗读**类界面，句子本身应该是主体；分数挂在词下面时，
"是 volume 拖低了总分"是**一眼**可见的，不需要在数字与标签之间来回对照。

### 3.2 评分只留最新一次（否决了多行尝试记录）

**否决方案**：追加式写入，一句话多行，保留每次尝试。

理由：
1. **追加比覆盖更简单也更安全** —— 但收益（进步曲线）本次不做，
   而为它预留的表结构会成为长期负担
2. 覆盖式 upsert 一次写完，不会出现"同一句有 8 行、查询要挑最新"的复杂度
3. 用户明确选了"只留最新一次"

**代价（记在这里备查）**：日后要做进步曲线，需要新增尝试表，
且**此前累积的数据无法回溯**（旧记录已被覆盖）。这是明知的取舍。

### 3.3 逐词分只信有道返回的 `words[]`

不用 `sentences.english` 切词。原因见 §1.3：库里的标点是独立 token，
而 `words[]` 是有道自己的分词结果。两边不一致时，**以有道的为准** ——
因为分数是它给的，按库里的词去对分会对错位置。

**风险**：如果 `words[]` 漏掉某些词，逐词区就会少几个词。
**处理**：逐词区渲染成"有道给了分的词"，**不假设每个词都有分**；
实施前用真实录音验证一次 `words[]` 是否覆盖整句（见 §6.3）。

### 3.4 评语用规则拼，不调 AI

**否决方案**：调 DeepSeek 生成评语。

理由：规则能给出的信息**已经覆盖了 AI 的价值**，而 AI 要付出成本、延迟与降级复杂度：

| 规则能说的 | 依据 |
| --- | --- |
| "很棒！整体清晰流畅。" | 总分档位 |
| "volume 这个词可以重点练一下。" | `words[]` 里的最低分词 |
| "流利度偏低，试着连贯一些、少停顿。" | 维度分 |
| "有词没读全，注意别漏读。" | 完整度 < 100 |

这些都是**对着具体数据说的**，不是"继续加油"这类空话。AI 真正的增量在
**音标级诊断**（"为什么"），那是另一个功能（§2 非目标）。

**评语在服务端生成、只生成一次、随评分一起落库**：
- 客户端渲染两次不会跳字（跳字看起来像坏了）
- 历史回看时看到的是当初那句，不会重新生成

**减少重复感**：用"**不与上一句重复**"这条规则代替纯随机的碰运气 ——
上一句就在本行要被覆盖的数据里，顺手读出来即可。文案池见 §5。

### 3.5 与练习进度完全解耦

「句子完成」与「跟读评分」是**两个独立维度**：

- 大纲列表的**已完成**只由练习进度决定，跟读有没有分都不影响
- 有分显示小分数；**没分什么都不显示**（不显示 0 分、不显示"—"）
- 跟读的写入**绝不碰** `practice_records` / `review_queue` / `user_course_progress`

### 3.6 进入有历史分的句子时，卡片显示历史分

两种读法各有道理，用户选了这个：**显示**（附"3 天前"），点开详情复用同一个弹窗。
好处是"存进数据库的分"在练习页也看得到，而不是只能在大纲列表里露一眼。

### 3.7 数据模型：独立表 `pronunciation_scores`，一句话一行

```
UNIQUE (user_id, sentence_id)   ← 覆盖式更新的依据
```

| 列 | 类型 | 说明 |
| --- | --- | --- |
| `id` | varchar(36) PK | UUID |
| `user_id` | varchar(36) NOT NULL | |
| `sentence_id` | varchar(36) NOT NULL | |
| `score` | int NOT NULL | 总分 |
| `accuracy` / `fluency` / `integrity` | int NOT NULL | 三个维度 |
| `speed` | decimal(6,2) NULL | 语速，有道可能不给 |
| `words` | json NULL | **逐词分数，必须存** —— 否则历史分点开"查看详情"没有逐词数据。形状固定为 `Array<{ word: string; score: number \| null }>`：**必须允许 `score: null`**（有道的字段可能缺失，用 0 兜底会把"没给分"显示成"0 分"） |
| `comment` | varchar(500) NULL | **评语也存** —— 否则重开详情会生成一句不一样的话。为 `NULL` 时界面**不渲染评语区**（不留空行、不显示占位） |
| `created_at` / `updated_at` | datetime | 界面上的"3 天前"用 **`updated_at`**（即最近一次评分的时间）。因为一句话只有一行，`created_at` 是**第一次**录这句的时间，拿它显示"3 天前"会与最近一次评分的时间不符 |

**为什么不挂在 `practice_records` 上**：那张表是"每次作答一行"，一句可以有多行；
而跟读要的是"一句一行取最新"。挂上去会变成"取最新一行、而它可能没有跟读分"，
查询别扭且容易写错。独立表 + `UNIQUE` 才是它的形状。

### 3.8 会话内显示分数变化（`61 → 84`）

"再试一次"之后，如果本次会话里已有上一次的分，卡片上顺手显示变化。
这**不需要新字段**（用客户端会话内 state），却是"再试一次"最直接的反馈。

## 4. 接口

| 改动 | 内容 |
| --- | --- |
| `POST /api/youdao/evaluate` | 评分成功后 **upsert** 一行（额度校验已在这里，不必多一次往返）。**写库失败不影响评分返回** —— 用户该看到分数，只是这次没存上，记日志 |
| `GET /api/courses/sentences` | 下发句子时 **LEFT JOIN** 带上该句的跟读分（省掉每句一次请求）。大纲弹窗与练习页共用这份数据 |

`LEFT JOIN` 而非 `INNER JOIN`：绝大多数句子没有跟读分，`INNER` 会把它们滤掉。

## 5. 评语文案池

四段可组合：**总评**（必出）→ **最低分词**（条件）→ **短板维度**（条件）→ **兜底**（条件）。

### 5.1 总评（按总分档位，每档 6 条）

**≥ 95**

1. 几乎无可挑剔，这句读得跟示范音一样。
2. 非常出色！发音和节奏都很到位。
3. 满分水准，这个句子你已经拿下了。
4. 近乎完美，听不出明显问题。
5. 这一遍非常干净，保持住。
6. 发音准确、节奏自然，很好。

**85 – 94**

1. 很棒！整体清晰流畅。
2. 读得不错，个别词还能再打磨一下。
3. 整体很稳，发音清楚。
4. 完成得很好，只有小地方可以更讲究。
5. 流畅自然，继续保持。
6. 很不错，细节上再抠一抠就更好。

**70 – 84**

1. 不错，意思都读出来了，但还能更清楚些。
2. 基本到位，注意几处容易含糊的地方。
3. 整体可以，节奏或个别音还可以更好。
4. 读对了，但还不够利落。
5. 听懂没问题，打磨一下会更好。
6. 已经上路了，把下面几点改掉会有明显进步。

**55 – 69**

1. 还差一口气，先慢下来把每个词读准。
2. 能听出你在读什么，但有几处明显偏了。
3. 别急，先求准再求快。
4. 有些词含糊过去了，逐个抠一下。
5. 还可以，但需要再练两遍。
6. 方向对了，准确度还得提上来。

**< 55**

1. 这句有点吃力，建议先听两遍示范音再录。
2. 不用急，先把句子读慢一点、读完整。
3. 有几处差得比较多，跟着示范音逐句跟读会更快。
4. 先别追求速度，把音读准是第一位的。
5. 这句还没过关，再听一遍示范音试试。
6. 慢慢来，一个词一个词过。

### 5.2 最低分词

**触发条件（两条同时满足，避免"全句都很好却单挑一个词"）**：

1. 最低分词 `< 75`
2. `句均分 - 最低分词 >= 12`

第二条是防止这种情况：整句 88 分、各词 85~92，此时点名词汇会让用户以为
自己那个词读错了，其实只是相对低一点。**只有在它真的拖了后腿时才点出来。**

`${word}` 为最低分的那个词。

1. `${word} 这个词可以重点练一下。`
2. `其中 ${word} 读得最不清楚。`
3. `${word} 的发音再注意一下。`
4. `卡在 ${word} 上了，单独读几遍。`
5. `${word} 是这句里最弱的一环。`
6. `下次重点盯一下 ${word}。`

> **注意措辞的边界**：没有音素级数据，所以只能说"读得最不清楚"，
> **不能说**"volume 的 /v/ 发成了 /w/"。后者是编造，属于 §2 的非目标。

### 5.3 短板维度（条件：该维度 < 75）

**准确度**

1. 准确度偏低，注意每个词的音要发全。
2. 有些音发得不够到位，慢一点会更好。
3. 先把音读准，再考虑速度。
4. 个别词的口型没打开，音就飘了。
5. 准确度是这次的主要短板。

**流利度**

1. 流利度偏低，试着连贯一些、少停顿。
2. 中间停顿有点多，可以顺着读下去。
3. 读得有点断，试着把词连起来。
4. 节奏可以再顺一点，不用一个词一个词地蹦。

**完整度**

1. 有词没读全，注意别漏读。
2. 句子没读完整，最后几个词也要读出来。
3. 有吞音或漏读，把每个词都交代清楚。
4. 完整度不够，读的时候别跳词。

### 5.4 兜底

| 条件 | 文案 |
| --- | --- |
| 总分 < 30 | 可能是没录到声音，或者离麦克风太远 —— 确认一下再试。 |
| 总分 = 100 | 满分，示范级表现。 |

**优先级**：`总分 < 30` 与 `总分 = 100` 都是**覆盖规则** —— 命中时直接用它，
**不再**拼 §5.2 的最低分词与 §5.3 的短板维度。理由：< 30 时那多半是录音问题，
再给发音建议是误导；= 100 时没有短板可指。（`= 100` 覆盖 §5.1 的 ≥ 95 档。）

**总分 < 30 单独处理**：极低分通常**不是发音问题而是录音问题**
（没开麦、离太远、录到了别的声音）。这时给发音建议是误导，该提示检查设备。

**`words[]` 为空时**：不输出 §5.2 那一段（其余照常），**不提示"没有逐词数据"** ——
那对用户是噪声，也像是在暴露系统异常。

## 6. 验证

### 6.1 单测

- 评语：各档位取词正确、最低分词正确、短板维度只在 < 75 时出现、
  总分 < 30 走录音提示、100 分走满分文案、`words[]` 为空时不出现逐词段
- 评语：**不与上一句重复**这条规则（传入上一句时必定换一条）
- 池子：每档至少 6 条且无重复串（防止复制粘贴时漏改）
- 逐词分 `null` **不渲染成 0**（现有 `pronunciation.test.ts` 已守住，本次扩充）

### 6.2 e2e

- 同一句连续两次评分：表里**仍只有一行**，且内容是最新那次
- `/api/courses/sentences` 对**有**跟读分的句子带上该字段、对**没有**的**字段不出现**
  （不是 `null`、不是 0）
- 没有跟读分时，大纲列表不渲染任何分数占位

> 注：e2e 环境屏蔽了 `YOUDAO_APP_KEY`，评分接口会返回 503（`unconfigured`）。
> 所以落库与下发这两条用**直接写库 + 读接口**验证，不依赖真实评分调用。

### 6.3 实施前必须真机验证的一件事

**有道返回的 `words[]` 是否覆盖整句所有词。**

拿一句含标点的真实句子（如 `Seven , eight , don't be late !`）录一次，
对比 `words[]` 的长度与内容。若它漏词，逐词区按 §3.3 的约定渲染成
"有道给了分的词"，**不补空位、不显示未给分的词**。

### 6.4 迁移

- 新表 → 显式 `DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci`
- 手工执行（仓库无迁移执行器），执行前按 `db-backup/` 惯例备份
- `schema.ts` 与 `db/README.md` 的迁移索引同步更新

## 7. 回滚

- 代码回滚即可：界面退回内联评分，`pronunciation_scores` 表留着不读不写，无副作用
- 不需要回滚迁移（新表不影响任何既有查询）

## 8. 未决

- 进步曲线（需要多行尝试记录，见 §3.2 的代价）
- 音标级诊断（§2 非目标）
